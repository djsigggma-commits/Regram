# Встроенный Telegram WebSocket-транспорт

## Статус

Встроен **основной сетевой функционал**, а не интерфейс и сервис целого стороннего приложения. Настройка: **Настройки → Настройки re:gram → Функционал re:gram → Обход блокировки**, переключатель **«Использовать обход»**. Переименование и удаление длинного описания под настройками включены в последнюю подписанную пересборку APK 1.4.8.9; новые названия и отсутствие информационной строки проверены в ресурсах/DEX готового APK. Ссылка на исходники и авторов в настройках оставлена; технические ограничения описаны в этом документе. По умолчанию выключены сам транспорт и прямой TCP-резерв. **Cloudflare-маршруты по умолчанию включены, размер WS-пула — 4** на недавно использованный маршрут. Сохранённые пользовательские значения Cloudflare не перезаписываются. Размер пула можно выбрать в настройках: 0 (без прогрева), 2, 4 или 8. Настройки общие для всех аккаунтов; изменение закрывает текущие транспортные сессии и переподключает tgnet.

Пул и значения по умолчанию включены в [пересобранный подписанный APK 1.4.8.9](BUILD_RELEASE_1.4.8.9.md). Номер версии и versionCode сохранены по запросу владельца; прежний APK без пула помещён в `artifacts/archive/`. Различайте сборки по SHA-256 из отчёта.

Не требуется устанавливать TG WS Proxy, запускать foreground service, разрешать уведомления, передавать `tg://proxy`, выбирать локальный порт или импортировать секрет. Старые SOCKS/MTProto/WEB-прокси не изменяются и при включении имеют приоритет.

## Архитектура

```text
Connection / MTProto / AES-CTR (tgnet C++)
       ↕ непубличная socketpair внутри процесса; без bind/listen
TelegramWebSocketTransport + WebSocketPacketFramer (Java)
       ↕ WSS, TLS и RFC 6455 через существующий OkHttp
Telegram DC / Cloudflare-маршрут
```

- `Connection.cpp` выбирает допустимые DC 1–5, 203 и передаёт известные tgnet DC/media/test признаки. CDN, временные bootstrap-соединения и проверки внешних прокси не перехватываются.
- JNI возвращает tgnet файловый дескриптор `ParcelFileDescriptor.createSocketPair()`. DNS, TLS, HTTP upgrade и чтение Java не блокируют native network thread. Дескриптор tgnet — неблокирующий, управляется существующим epoll.
- После успешного удалённого подключения Java сначала отправляет однобайтовый внутренний readiness-marker. Он удаляется в `ConnectionSocket` и не попадает в MTProto. До этого EPOLLOUT выключен. При ошибке дескриптор закрывается, срабатывают штатные reconnect/timeout/request механизмы tgnet.
- Обычный MTProto остаётся в C++: unkeyed obfuscated abridged (`0xef`), DC в init-пакете, прежние ключи аккаунта/сессии и шифрование. Прокси-секрет не генерируется и не используется.
- `WebSocketPacketFramer` читает ровно 64 байта init, затем копией AES-CTR-курсора распознаёт длины коротких/длинных abridged-пакетов, включая quick-ACK bit. Каждое полное сообщение отправляется отдельным WS binary message; ciphertext не изменяется. Простой перевод произвольных TCP-чанков в WS-фреймы здесь недостаточен.
- WSS: `kwsN.web.telegram.org/apiws`; для медиа сначала `kwsN-1.web.telegram.org`, затем второй адрес. Test backend использует `/apiws_test`, 203 выбирает домен DC2, как upstream.
- Cloudflare по умолчанию включён внутри WS-транспорта, его можно выключить отдельно: сначала до двух доступных базовых доменов из перемешанного списка, затем оба прямых WSS-адреса. Адрес строится как `kwsN.<base-domain>`. Можно задать до 20 собственных базовых доменов без схем, портов и путей; пустая строка выбирает встроенные 20 доменов upstream. После HTTP 429 — cooldown 45 секунд.
- Прямой TCP-резерв работает **только после явного включения**, до начала MTProto-обмена и только после неудачи WSS-маршрутов. Используются адрес и порт, выбранные tgnet. Уже начатый зашифрованный поток не переигрывается через другой сервер: вместо этого соединение закрывается для штатного переподключения.
- Настоящий WS-пул хранит до 4 заранее открытых, ещё не использованных MTProto-соединений на ключ `(DC, media, test, Cloudflare, domains)`. Пул заполняется после первого успешного подключения и автоматически пополняется после выдачи сокета. Сокет после выдачи никогда не возвращается в пул; MTProto init и пользовательские данные не отправляются при прогреве. Сообщения на непривязанный сокет приводят к его закрытию.
- Максимум 16 idle/pending соединений пула суммарно, два фоновых warmup-worker и ограниченная очередь заданий. Просроченные (90 секунд) и закрытые сокеты отбрасываются; после 120 секунд без использования маршрута его пул закрывается. Обслуживание — раз в 5 секунд, при отсутствии пулов таймер отменяется; при сбоях применяется backoff 5–60 секунд. Выключение транспорта, изменение настроек, отсутствие сети и внешний прокси останавливают прогрев; старые задания не могут заново заполнить сброшенный пул.
- Ограничение: 64 одновременно активных транспортных сессии; очередь отправки не превышает 16 MiB. Размер MTProto-пакета ограничен до выделения памяти. Socketpair обеспечивает backpressure; Java-запись в неё имеет таймаут 5 секунд. Освобождение идемпотентно, `shutdown` будит заблокированные чтения/записи. OkHttp ping — 30 секунд.
- Диагностика содержит до 80 событий, число активных сессий, target/idle/pending пула и события pool hit/miss; без содержимого сообщений, ключей, пользовательских доменов, адресов и идентификаторов аккаунтов. Список событий только в памяти.

## Безопасность и отличия от исходного приложения

**Это не VPN и не режим скрытия IP.** Звонки, CDN и bootstrap сохраняют прежний транспорт и могут подключаться напрямую даже при выключенном TCP-резерве. Внешний включённый прокси полностью имеет приоритет над новой настройкой.

Cloudflare-маршруты — сторонняя инфраструктура. Их операторы могут видеть IP и метаданные соединения; защита MTProto остаётся прежней. Доступность конкретных доменов и маршрутов не гарантируется.

Из исходного Rust-приложения **не перенесены**:

- отключение проверки TLS/подписей, insecure/plain WS и SNI-fronting;
- локальный MTProxy-сервер, FakeTLS для локального клиента и раздача прокси другим приложениям;
- foreground service, tile, boot receiver, updater и независимый Compose-интерфейс;
- фоновое скачивание списка сторонних доменов, DoH-обходы, ручные IP-подмены DC.

Пул заранее открытых WS-соединений реализован в `WebSocketWarmPool` и использует тот же проверяемый WSS/OkHttp-транспорт, что и обычные подключения.

Сертификаты и hostname проверяются стандартным TLS OkHttp/Android. HTTP-редиректы не разрешены. Если маршрут работает лишь при отключённой TLS-проверке, он будет отклонён.

## Проверки

```sh
python3 -m pytest tests/test_telegram_websocket_transport.py -q
```

Тест исполняет настоящие AES-CTR-векторы JVM: init, короткие/длинные пакеты, quick-ACK, непрерывность cipher cursor, фрагментация по 1/3/64/8192 байтам, слияние пакетов, EOF, усечение, неверный протокол и превышение лимита. Дополнительный JVM-тест пула проверяет выдачу четырёх разных сокетов, пополнение, изоляцию маршрутов, TTL, idle-timeout, backoff, лимит pending+idle, выключенный прогрев, отмену старых заданий после reset и отказ executor. Остальные проверки фиксируют JNI-сигнатуры, приоритет внешних прокси, отсутствие silent TCP fallback и ослабления TLS, единые defaults UI/runtime, локализации и навигацию.

После изменения пула проверено: полный набор — **469 passed, 31 skipped, 27 subtests passed**; WSS + навигация — **11 passed**; `:TMessagesProj:compileDebugJavaWithJavac` — **BUILD SUCCESSFUL** (включая Kotlin/resources). Это проверки исходников/компиляции, не реальные сетевые соединения на устройстве. Дополнительно собран release APK с пулом: R8, подпись, JNI-контракты, наличие `WebSocketWarmPool` и значения `DEFAULT_POOL_SIZE=4`, `DEFAULT_CLOUDFLARE=true` проверены непосредственно в post-R8 DEX.

До изменения пула проверено в рабочем окружении:

- полный набор `tests`: **467 passed, 31 skipped**, 27 subtests passed (JDK 21 в `PATH`);
- отдельный набор WSS + навигация + защита от возврата удалённого proxy-runtime: **10 passed**;
- `:TMessagesProj:compileDebugJavaWithJavac`: успешно, включая Kotlin/resources;
- NDK arm64 `clang++ -fsyntax-only`: все четыре изменённых native translation units прошли проверку; в прежнем коде `ConnectionsManager.cpp` остаются предупреждения.

Перечисленные исходные проверки сами по себе не заменяют native link и проверку готового APK. Дополнительно собран [подписанный release APK 1.4.8.9](BUILD_RELEASE_1.4.8.9.md): native link, R8, подпись и реальные WSS DEX/JNI-контракты прошли проверку. **На устройстве и реальной сети транспорт ещё не проверен.**

Перед выпуском на устройстве проверить:

1. Выключенная настройка: обычное подключение, SOCKS/MTProto/WEB, проверки прокси без изменений.
2. WSS: вход/авторизация, несколько аккаунтов, сообщения, короткие и длинные загрузки, push/фон, смена Wi-Fi ↔ мобильная сеть.
3. Cloudflare: собственный/встроенный домен, недоступный маршрут, HTTP 429, неверный сертификат, таймаут upgrade, переход к следующему маршруту.
4. TCP-резерв выключен: поддерживаемый DC не уходит в TCP при сбое WSS; включён — получает отдельное событие диагностики. Проверять отдельно от CDN/bootstrap/calls, которые не охвачены настройкой.
5. Быстрые переключения режима и backend, закрытие сокета во время DNS/upgrade/загрузки, отсутствие утечек FD/потоков и воспроизведения старых MTProto-пакетов.
6. Пул: после первого успешного WSS проверить idle=4, выдачу без повторного upgrade, последующее пополнение, уничтожение просроченных сокетов и остановку прогрева при внешнем прокси/выключении/смене сети. Проверить значения 0/2/4/8 и сохранённое выключение Cloudflare после обновления.
7. Проверить фоновые ограничения Samsung/других OEM, расход памяти/батареи и поведение при больших медиафайлах.

До прохождения этих сценариев функция остаётся **экспериментальной**.
